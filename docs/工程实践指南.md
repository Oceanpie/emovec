## 1. 并发：同时干多件事

### 1.1 为什么要并发

假设你要调用 153 次 embedding API，每次耗时 0.5 秒：

| 方式 | 总耗时 | 说明 |
|---|---|---|
| 串行（一个一个来） | 153 × 0.5s = **76 秒** | 大部分时间在等网络响应 |
| 5 并发 | 153 ÷ 5 × 0.5s ≈ **15 秒** | 5 个请求同时发出 |

**核心原理**：API 调用是 I/O 密集型任务——你的代码大部分时间在"等网络回复"。并发就是让多个"等待"同时进行，而不是排着队等。

### 1.2 ThreadPoolExecutor：本项目用的方案

Python 标准库 `concurrent.futures.ThreadPoolExecutor` 是最简单的并发方案。

**基本模式**（本项目 `build_prototype.py` 的写法）：

```python
from concurrent.futures import ThreadPoolExecutor, as_completed

def embed_one(item):
    """单个任务：编码一个条目"""
    title, desc = item
    vec = get_embedding(desc)           # 调用 API，等网络
    return title, vec

with ThreadPoolExecutor(max_workers=5) as executor:
    # 提交所有任务
    futures = {executor.submit(embed_one, item): item[0] for item in to_embed}
    # 按完成顺序收集结果
    for future in as_completed(futures):
        title = futures[future]
        try:
            title, vec = future.result()
            new_vec_lookup[title] = vec
        except Exception as e:
            failed.append(title)
```

**关键概念**：
- `max_workers=5` → 5 个线程同时工作
- `executor.submit(func, arg)` → 把任务扔进线程池，立刻返回一个 Future 对象
- `as_completed(futures)` → 哪个先完成就先处理哪个（不是提交顺序）
- `future.result()` → 获取结果；如果任务抛异常，这里会 re-raise

### 1.3 线程安全：并发写文件的问题

多个线程同时往同一个列表/文件写东西，会出问题：

```python
# ❌ 危险：两个线程可能同时 append，导致数据错乱
results.append(result_entry)
save_results(file_path, results)
```

解决方法：加锁（`Lock`），保证同一时刻只有一个线程能写：

```python
from threading import Lock

write_lock = Lock()

def evaluate_one(sample):
    result = call_api(sample)    # 并发执行，没问题

    with write_lock:             # 排队写入
        results.append(result)
        save_results(path, results)
```

**本项目 `eval_llm_judge.py` 的写法就是这样**——API 调用在锁外面并发执行，只有写入操作在锁内串行执行。

### 1.4 并发数怎么选

| 场景 | 建议并发数 | 原因 |
|---|---|---|
| Embedding API（ModelScope/SiliconFlow） | 5-10 | API 有速率限制，太高会被 429 |
| LLM Chat API（DeepSeek） | 5-20 | 看你的 quota，DeepSeek 限制较宽 |
| 本地计算（numpy、无网络） | CPU 核心数 | 用 `ProcessPoolExecutor` 而不是线程 |
| 不确定 | 先用 5 | 保守起步，观察 API 返回的错误率 |

**经验法则**：先用低并发跑，如果没报错就逐步提高。出现 429 (Rate Limit) 就降下来。

### 1.5 ThreadPoolExecutor vs asyncio

| | ThreadPoolExecutor | asyncio |
|---|---|---|
| 学习成本 | **低**（就是函数 + submit） | 高（async/await 整套生态） |
| 适合场景 | 调用同步 SDK（如 `openai` 库） | 需要极高并发（1000+） |
| 本项目 | ✅ 所有脚本都用这个 | 没必要 |
| 依赖 | 标准库，零依赖 | 需要 `aiohttp` 等异步库 |

**结论**：本项目 153-10000 条的规模，`ThreadPoolExecutor` 完全够用。

## 2. 增量恢复：崩了不用从头来

### 2.1 问题场景

你跑一个处理 10000 条数据的脚本，跑到第 7000 条时：
- 网络断了
- 电脑休眠了
- API 限流了
- 手动 Ctrl+C 了

**没有增量恢复** → 从第 1 条重新跑，前 7000 条白干了。

**有增量恢复** → 从第 7001 条接着跑。

### 2.2 方案一：Skip-Existing（本项目在用）

**思路**：开始前检查哪些结果已经存在，跳过它们。

```python
# 本项目 build_prototype.py 的做法
existing_map = build_existing_index_map(existing_meta)   # 加载已有结果
skip_set = set(existing_map.keys())                      # 构建跳过集合

to_embed = [
    (entry, desc)
    for entry, desc, redirect in entry_data
    if not redirect and entry["title"] not in skip_set   # 过滤掉已完成的
]
print(f"待嵌入: {len(to_embed)}，复用: {len(skip_set)}")
```

**优点**：简单，不需要额外的 checkpoint 机制——输出文件本身就是 checkpoint。
**缺点**：只适用于"每条输入产出一个独立输出文件"的场景。

### 2.3 方案二：JSON Checkpoint Store

**思路**：专门用一个 JSON 文件记录每条的处理状态。

```python
# 加载已有的评价结果
cache_path = TEST_DIR / "llm_judge_results.json"
existing_results = {}

if not args.force and cache_path.exists():
    with open(cache_path, encoding="utf-8") as f:
        cached = json.load(f)
    existing_results = {r["index"]: r for r in cached.get("results", [])}
    print(f"已有缓存: {len(existing_results)} 条评价结果")

# 只处理还没评价的
for sample in samples:
    idx = sample["index"]
    if idx in existing_results and not args.force:
        results.append(existing_results[idx])    # 直接复用
        continue
    to_evaluate.append(sample)                   # 这条需要处理
```

**本项目 `eval_llm_judge.py` 的做法**——每条评价完成后立刻存盘，崩溃后重跑只补缺的。

### 2.4 方案三：状态机 + 原子 Checkpoint

适用于更复杂的流水线（多步骤，步骤之间有依赖）：

```
每条数据有 4 种状态：
  PENDING → RUNNING → DONE
                    → NEEDS_REVIEW（失败，需人工介入）
```

启动时：把所有 `RUNNING` 状态的条目重置为 `PENDING`（上次崩溃留下的），然后只处理 `PENDING` 的条目。

**本项目暂时用不到**——我们的脚本都是单步骤的（编码 / 评价），不需要状态机。

### 2.5 Checkpoint 粒度：多久存一次

| 粒度 | 适用场景 | 风险 |
|---|---|---|
| 每条完成后存 | API 调用贵（LLM 标注） | I/O 开销大（但 JSON 写入很快） |
| 每 N 条存一次 | 处理上万条，每条很便宜 | 崩溃后最多丢失 N 条的进度 |
| 最后才存 | 快速脚本，重跑成本极低 | 崩溃后全部重跑 |

**本项目的情况**：
- `build_prototype.py`：每次跑完后统一存（因为 API 调用贵，但增量跳过机制兜底）
- `eval_llm_judge.py`：**每条完成后立即存**（因为 LLM 评价每条都要花钱，不能丢）

### 2.6 `--force` 参数：绕过缓存

所有增量恢复都应该提供一个 `--force` 参数，忽略缓存从头重跑：

```python
parser.add_argument("--force", action="store_true", help="忽略缓存，全部重跑")
```

用途：代码改了、prompt 改了、结果可能有变化时，强制全量重跑。

## 3. 容错与重试：API 不靠谱怎么办

### 3.1 API 调用会出什么错

| 错误类型 | 原因 | 应对 |
|---|---|---|
| **429 Rate Limit** | 请求太快了 | 等一会儿再试（退避） |
| **500/502/503** | 服务器临时故障 | 重试 |
| **Timeout** | 网络慢或请求太大 | 重试，或减小请求 |
| **400 Bad Request** | 请求格式有错 | **不要重试**，检查请求内容 |
| **401 Unauthorized** | API Key 无效 | **不要重试**，检查配置 |

### 3.2 指数退避（Exponential Backoff）

**核心思路**：失败后不要立刻重试，等越来越长的时间。

```
第 1 次失败 → 等 1 秒再试
第 2 次失败 → 等 2 秒再试
第 3 次失败 → 等 4 秒再试
第 4 次失败 → 等 8 秒再试
```

```python
import time

for attempt in range(max_retries):
    try:
        return call_api(text)
    except Exception as e:
        if attempt == max_retries - 1:
            raise    # 最后一次还是失败，向上抛异常
        wait = 2 ** attempt    # 1, 2, 4, 8...
        time.sleep(wait)
```

**加随机抖动（Jitter）更佳**：多并发时，如果所有线程同时失败、同时等待、同时重试，会造成"惊群效应"。加随机抖动打散重试时间：

```python
import random

wait = 2 ** attempt + random.uniform(0, 1)    # 1~2, 2~3, 4~5, 8~9...
```

### 3.3 Tenacity 库：生产级重试

`tenacity`（8500+ ⭐）是 Python 最流行的重试库，一行装饰器搞定：

```python
from tenacity import retry, stop_after_attempt, wait_exponential, retry_if_exception_type

@retry(
    stop=stop_after_attempt(3),                     # 最多重试 3 次
    wait=wait_exponential(multiplier=1, max=60),     # 指数退避，最大等 60 秒
    retry=retry_if_exception_type((TimeoutError, ConnectionError)),  # 只重试这些错误
)
def call_api(text):
    resp = client.chat.completions.create(...)
    return resp.choices[0].message.content
```

**不用 tenacity 的手动写法**（本项目 `eval_llm_judge.py`，简化版）：

```python
def call_llm(client, model, text, scores_a, scores_b, max_retries=3):
    last_err = None
    for attempt in range(max_retries + 1):
        try:
            resp = client.chat.completions.create(...)
            return parse_response(resp)
        except Exception as e:
            last_err = e
            if attempt < max_retries:
                time.sleep(5 * (attempt + 1))    # 5, 10, 15 秒
    return {"error": "api_failed", "detail": str(last_err)}
```

> ⚠️ **注意**：上面的代码用了 `except Exception`，会重试**所有**异常（包括不该重试的 400、401 等）。这是简化写法。生产环境建议只重试临时性错误（429、500/502/503、Timeout），对客户端错误直接抛出，参考 Section 3.7 的分类表。

### 3.4 多 Provider Fallback

本项目有 ModelScope 和 SiliconFlow 两个 embedding provider。主 provider 挂了自动切换：

```python
# src/embedding.py 的 fallback 逻辑
for provider in providers:
    try:
        return call_provider(provider, text)
    except Exception:
        continue
raise AllProvidersFailedError()
```

**这是 cascading fallback 模式**——依次尝试，第一个成功就返回。适用于多个 API 提供相同服务的场景。

### 3.5 部分失败处理

处理 153 条数据时，第 47 条失败了怎么办？

**❌ 错误做法**：一条失败，整个脚本退出，前面 46 条白干了。

**✅ 正确做法**：收集失败，继续处理剩余的，最后报告失败列表。

```python
failed = []

for future in as_completed(futures):
    try:
        result = future.result()
        save(result)
    except Exception as e:
        failed.append(item_id)
        print(f"  失败: {item_id} - {e}")

# 最后报告
if failed:
    print(f"\n失败条目 ({len(failed)}): {', '.join(failed)}")
    print("重新运行即可重试（增量模式会跳过成功的）")
```

### 3.6 OpenAI SDK 自带重试

**很多人不知道**：OpenAI Python SDK 已经内置了重试机制。

```python
from openai import OpenAI

# 默认 max_retries=2，自动重试以下错误：
# - 429 Rate Limit
# - 500/502/503 服务器错误
# - 网络连接超时
client = OpenAI(max_retries=3)     # 改为 3 次

# 每次请求单独设置
client.with_options(max_retries=5).chat.completions.create(...)
```

**注意**：如果同时用了 tenacity 和 SDK 的内置重试，会导致重试被放大。比如 SDK 重试 3 次 + tenacity 重试 3 次 = 最多 9 次请求。**选一个就行**。

### 3.7 错误分类：哪些该重试，哪些不该

| 错误类型 | HTTP 状态码 | 重试？ | 原因 |
|---|---|---|---|
| 速率限制 | 429 | ✅ 重试（加退避） | 服务器说"慢一点"，等一下就好 |
| 服务器故障 | 500/502/503 | ✅ 重试 | 临时性问题，过一会可能恢复 |
| 网络超时 | Timeout | ✅ 重试 | 网络/服务器慢，再试一次 |
| 请求格式错 | 400 | ❌ 不重试 | 你的代码有问题，重试也没用 |
| 认证失败 | 401 | ❌ 不重试 | API Key 错了，重试也不会成功 |
| 权限不足 | 403 | ❌ 不重试 | 配额用完或没有权限 |
| 资源不存在 | 404 | ❌ 不重试 | 模型名拼错了之类的 |

**关键原则**：只有"服务器端的临时问题"才值得重试。客户端的错误（代码 bug、配置错误）重试只会浪费时间。

## 4. 幂等性：跑两遍结果不变

### 4.1 什么是幂等性

**幂等** = 同一个操作执行一次和执行多次，效果一样。

- `x = 5` 是幂等的（赋值 100 次还是 5）
- `x = x + 1` 不是幂等的（每次执行 x 都变大）

### 4.2 为什么脚本需要幂等性

你的脚本跑了一半崩溃了，重跑时：
- 已完成的 46 条不会重新处理（skip 机制）
- 失败的第 47 条会被重试
- **效果等同于**只跑了一次完整的

如果脚本不幂等——比如每次运行都 append 到同一个文件——那重跑就会产生重复数据。

### 4.3 本项目的幂等设计

| 脚本 | 幂等机制 |
|---|---|
| `build_prototype.py` | 已有向量的条目跳过；`--force` 全量重跑 |
| `eval_instruction_ab.py` | Group B 向量缓存为 `.npy` 文件，存在就加载 |
| `eval_llm_judge.py` | 已评价的条目（按 index）跳过，每条完成后存盘 |
| `label_emotions.js` | 每个条目 5 轮标注，已有完整 5 轮的跳过 |

## 5. 原子写入：别写出半截文件

### 5.1 问题

写 JSON 文件时，如果写到一半进程崩了：

```json
{"entries": [{"title": "joy", "vector": [0.1, 0.2, 0.3,   ← 进程崩了，文件截断在这里
```

下次加载这个文件 → `json.loads()` 报错 → 数据全丢了。

### 5.2 解决：先写临时文件，再原子重命名

```python
import tempfile, os

def atomic_write_json(path, data):
    """原子写入 JSON 文件"""
    dir_name = os.path.dirname(path)
    fd, tmp_path = tempfile.mkstemp(dir=dir_name, suffix=".tmp")
    try:
        with os.fdopen(fd, "w", encoding="utf-8") as f:
            json.dump(data, f, indent=2, ensure_ascii=False)
        os.replace(tmp_path, path)    # 原子操作：要么成功，要么不变
    except BaseException:
        os.unlink(tmp_path)           # 失败了删掉临时文件
        raise
```

**原理**：`os.replace()` 是原子操作——操作系统保证文件名指向的内容瞬间切换，不存在"写了一半"的状态。

**本项目目前没用这个**——`save_prototype_store()` 和 `save_results()` 都是直接 `json.dump`。对于 153 条数据来说风险很低（写入很快），但如果扩展到更大数据集建议加上。

> **Windows 注意**：`os.replace()` 在 Windows 上也是原子的，但要求源文件和目标文件在**同一个卷（盘符）**上。`tempfile.mkstemp(dir=...)` 中 `dir` 必须和目标路径同卷。本项目所有文件都在同一目录下，不存在这个问题。

### 5.3 临时文件必须在同一目录

```python
# ❌ 错误：跨文件系统 rename 不是原子的
tempfile.mkstemp(dir="/tmp")

# ✅ 正确：同目录下创建临时文件
tempfile.mkstemp(dir=os.path.dirname(target_path))
```

## 附录 A：快速参考模板

### 并发 + 增量恢复 + 容错 的标准模板

```python
import json, os, time, random, argparse
from pathlib import Path
from concurrent.futures import ThreadPoolExecutor, as_completed
from threading import Lock

def main():
    parser = argparse.ArgumentParser()
    parser.add_argument("--force", action="store_true")
    parser.add_argument("--workers", type=int, default=5)
    args = parser.parse_args()

    # 1. 加载数据
    items = load_items()
    cache_path = Path("output/results.json")

    # 2. 增量恢复：加载已有结果
    done = {}
    if not args.force and cache_path.exists():
        with open(cache_path, encoding="utf-8") as f:
            cached = json.load(f)
        done = {r["id"]: r for r in cached.get("results", [])}
    pending = [item for item in items if item["id"] not in done]
    print(f"待处理: {len(pending)}, 已完成: {len(done)}")

    # 3. 并发处理
    results = list(done.values())
    failed = []
    write_lock = Lock()

    def process_one(item):
        result = call_api_with_retry(item)    # 含重试逻辑
        entry = {"id": item["id"], "result": result}
        with write_lock:
            results.append(entry)
            save_results(cache_path, results)    # 每条完成后存盘
        return entry

    with ThreadPoolExecutor(max_workers=args.workers) as executor:
        futures = {executor.submit(process_one, item): item for item in pending}
        for future in as_completed(futures):
            try:
                future.result()
            except Exception as e:
                failed.append(futures[future]["id"])
                print(f"  失败: {futures[future]['id']} - {e}")

    if failed:
        print(f"失败: {len(failed)}/{len(pending)}. 重跑即可重试。")

def is_retryable(e):
    """判断是否值得重试：只有临时性错误才重试"""
    if hasattr(e, "status_code"):
        return e.status_code in (429, 500, 502, 503, 504)
    return isinstance(e, (TimeoutError, ConnectionError, ConnectionResetError))

def call_api_with_retry(item, max_retries=3):
    last_err = None
    for attempt in range(max_retries + 1):
        try:
            return call_api(item)
        except Exception as e:
            if not is_retryable(e):
                raise    # 客户端错误（400/401/403），不重试，直接抛出
            last_err = e
            if attempt < max_retries:
                wait = (2 ** attempt) + random.uniform(0, 1)
                time.sleep(wait)
    raise last_err

def save_results(path, results):
    """非原子写入（简单版）。生产环境建议用 atomic_write_json。"""
    with open(path, "w", encoding="utf-8") as f:
        json.dump({"results": results}, f, indent=2, ensure_ascii=False)
```
